## ADR-001: Claude Code conditional hooks (`if` field)

**Date:** 2026-03-30
**Status:** Applied
**Ticket:** SAM-218

### Context

Claude Code v2.1.85+ supports an `if` field on hook handlers that uses permission rule syntax (e.g., `Bash(git *)`) to pre-filter which tool calls spawn the hook process. Without it, every Bash call spawns all Bash-matcher hook processes — they run and exit immediately if the command doesn't match, wasting startup overhead.

### Decision

Apply `if` field filtering to Bash hooks that do internal command matching. Move the filtering to the Claude Code runtime level so hook processes only spawn when they have work to do.

### Changes applied to `~/.claude/settings.json`

| Hook | `if` condition | Before |
|------|----------------|--------|
| `conventional_commits.py` | `Bash(git commit *)` | spawned on every Bash call |
| `tsc_precommit.py` | `Bash(git commit *)` | spawned on every Bash call |
| `git_safety.py` | `Bash(git *)` | spawned on every Bash call |
| `pnpm_enforcer.py` | `Bash(npm *)` + `Bash(yarn *)` (two entries) | spawned on every Bash call |
| `trauma_guard.py` | none (unchanged) | dynamic JSONL patterns — must run on all Bash |

### Corresponding script simplifications

- `conventional_commits.py`: removed `if 'git commit' not in cmd: sys.exit(0)` (now pre-filtered)
- `tsc_precommit.py`: removed `if "git commit" not in cmd: sys.exit(0)` (now pre-filtered)
- `pnpm_enforcer.py`: removed `re.search(npm|yarn)` early-exit guard (now pre-filtered by two `if` entries)

### Hooks intentionally excluded

- `writing_guard.py`: auto-generated by `margin export profile` CLI; script changes would be overwritten on next export. The `Write|Edit` matcher would need to be restructured into per-extension handlers (10+ entries for `.md`, `.mdx`, `.txt`, `.html`, `.htm` × Write + Edit). Marginal gain vs complexity; deferred.
- `voice_loader.py`: same Write|Edit matcher restructuring required. Excluded for now.
- `trauma_guard.py`: patterns loaded at runtime from `~/.cass-memory/traumas.jsonl`; `if` field cannot express dynamic conditions.

### Validation

All hooks pass functional tests post-change:
- `conventional_commits.py`: blocks bad commit messages, passes good ones, exits silently on non-commit input
- `tsc_precommit.py`: syntax valid; only runs when `if` pre-filter passes
- `git_safety.py`: blocks `git push --force`, exits silently on non-git Bash
- `pnpm_enforcer.py`: blocks `npm install` in pnpm project, exits silently on git/other commands

### Notes

- `Bash(npm *)` catches all npm commands (including `npm --version`), not just install/add/etc. Wider than the previous subcommand filter, but acceptable — all npm use in pnpm projects should use pnpm.
- Multiple `if` values on one handler are not supported; OR conditions require separate handler entries (hence two entries for pnpm_enforcer).
- Glob brace expansion for Write/Edit (`Edit(*.{md,mdx})`) was not explored — deferred with writing hooks.

## ADR-002: Writing rules manager lives in Settings → Writing rules, upgraded in place

**Date:** 2026-10-12
**Status:** Applied

### Context

Rules could already be browsed, edited, archived and restored from Settings → Writing rules → Active rules. What was missing for anyone with more than a handful of rules: search, a way to see which rules the writing guard actually blocks, and a lighter archive flow.

### Decision

Upgrade the existing tab instead of building a second surface, and organise it by Benji Taylor's Family Values (simplicity, then fluidity, then delight; each depends on the one before) and the motion discipline of Josh Puckett's Interface Craft. Only their public summaries were read; the paid kit itself was not.

- **Simplicity (gradual revelation).** The first version put a search box, view toggle, three severity chips, two selects, checkboxes, badges and an Export button on screen at once, and the screen read as confusing. Now: one search box and a Filter button; each rule is one line (text, severity, chevron); opening a rule reveals why, example, metadata and actions in place, one at a time; checkboxes appear on hover and a bulk bar replaces the search row once something is selected; the review queue is a sentence ("Showing 2 new rules. Show all 3"). Jargon dropped: "signals" became "Flagged N times", "Blocked mechanically/Advisory" became "Enforced automatically/Guidance only". The Export button became a quiet "Changes reach Claude automatically. Sync now" line, since every edit already exports.
- **Fluidity.** A rule opens with a 200 ms blur/fade/4px rise (`--ease-entrance`), keyboard-initiated opens do not animate, and `prefers-reduced-motion` removes it (`annotations.css`, per `docs/motion-spec.md`). Archive is one step with an Undo notice, since archive is recoverable and a confirm step cost a click every time.
- **Delight.** Deliberately restrained: this is a settings-adjacent surface used rarely, so the frequency rule gives it a small budget.

### Not done

Creating a rule by hand needs a new Tauri command and a Rust migration-safe path; deferred. Rules still have no link back to the corrections that produced them.

### Revision (2026-10-13): one pipeline, three stages

Sam's review of the first pass: the whole UX, information architecture and content strategy needed work, not only the rules list. The audit found the real problem was structural. The section had four tabs-and-tiles ("Corrections", "Active rules", stat tiles, an import bar) for what is one pipeline, used internal words (corrections, synthesis, polarity, signals, export), and listed unreviewed synthesis candidates under "Active rules" even though the CLI never exports them. That last one was a correctness problem: the page told Sam rules were in effect that Claude never saw.

**IA.** The section is now three tabs in pipeline order, each with its count: **Notes → Suggested → Rules**. Notes are corrections from highlights; Suggested are rules Claude drafted from them (`source = synthesis-candidate`, not yet reviewed); Rules are what Claude actually follows. It opens on the stage that needs Sam: Suggested if anything waits, else Notes if notes are ready, else Rules. The stat tiles, the separate import bar and the filter-hint plumbing are gone; the style-guide import lives under Rules as "Add from style guide" and as the empty state.

**Content.** Every label was rewritten in a writer's words, not the schema's:

| Was | Now |
|---|---|
| Corrections / Inbox / Archive | Your notes / Not used yet / Already used |
| Active rules | Rules in use (in effect only) |
| Synthesize N pending | Copy prompt for Claude |
| Must-fix / Should-fix / Nice-to-fix | Must fix / Should fix / Nice to fix |
| kill-words / ai-slop / voice-calibration | Words to cut / AI tells / Voice |
| general | All writing |
| Flagged N times / signals | From N notes |
| Enforced automatically / Guidance only | "Checked automatically: Margin scans Claude's drafts for this" / "Claude is told this rule; nothing checks for it" |
| Not feedback / Dismiss | Not about writing / Remove |
| Accept → edit | Apply edit |
| Sync now | Resend all rules |
| Colored border and highlight-color dot | "Avoid this" / "Do more of this" in words |
| Set type | Choose writing type / For: Email |

**No unexplained labels (second pass, same day).** Sam: "it's unclear what labels mean." Rule adopted: no label relies on color, position or prior knowledge. Tab names say what they hold (Your notes, Suggested rules, Rules in use); each tab opens with one sentence saying what is there and what to do; colour-coded polarity became words; counts carry their noun ("1 rule"); the unexplained `/` shortcut hint was removed. "Blocked automatically" was also inaccurate: the guard checks detection patterns, must-fix kill words and must-fix heading patterns, and soft patterns only block in clusters on published files. `isChecked` now mirrors `GenerateWritingGuardPy` and the label says "Checked".

**Interaction.** Suggestions get Accept and Decline on the row, plus bulk accept and decline. Accepting now re-exports, so an accepted rule reaches Claude immediately (before, it waited for the next unrelated edit). Notes gained the same search, Filter button and bulk bar as Rules, so the three stages share one grammar.

### Revision 3 (2026-10-13): the style guide

Sam: "you didn't explore different designs at all", and Must fix vs Nice to fix was unclear. Four directions were mocked up and compared (a readable style guide, a review queue, a test bench, rules suggested in the reading margin). Sam chose the recommendation: the style guide as the screen, the queue's keyboard decisions, and the bench as a tool inside it. The margin direction stays a later project because it needs Margin to draft rules without the copy-paste trip through Claude.

**Strictness is two levels in the UI.** Tracing severity through the CLI showed only must-fix changes behaviour (the guard checks must-fix word bans and heading patterns; the review prompt always includes must-fix rules and marks must-fix prohibitions BLOCK). Should-fix and nice-to-fix differ only in the tag Claude reads. The app shows **Hard rule** (must-fix) and **Preference** (the other two); the database keeps all three values, and switching a preference to and from hard rule keeps its old value where it can.

**IA.** Two views: **Style guide** (home) and **Notes**. The guide reads as sentences grouped by writing type, then category, each led by "Hard rule", "Prefer" or "Suggested". Suggestions sit inline, underlined like a suggested edit, with Accept and Decline. A margin pane explains both strictness levels when nothing is selected; with a rule selected it shows the notes the rule came from (parsed from `synthesized-from:` in the rule's notes, the same format the backend uses), its strictness control, whether the guard checks it, and its actions. Keys: arrows or j/k move, A/D accept or decline a suggestion, H flips strictness, E edits, / searches.

**Try your rules.** `rules-bench.ts` is a browser copy of the guard's matching (kill words, prohibition patterns, heading patterns, soft pattern families, the two-family block rule). It says plainly that blocking only happens on published paths.

Dropped: checkbox bulk selection for rules in use (Accept all covers the common bulk action), and the per-category collapse.

## ADR-004: The writing profile loads in layers

**Date:** 2026-10-20 · **Status:** Accepted

### Context

Sam pointed at Antoine van der Lee's SwiftUI agent skill as a reference. Its content doesn't apply, but its shape does. Its entry file is about 150 lines: always-on rules, then a table routing to roughly 30 topic files the agent opens only when the task needs them. It uses "always/never" only for real mistakes and "consider" for everything else. It tells the agent to apply guidance only to the code it is changing. It gives separate steps for reviewing and for writing new code.

Margin's export did the opposite on all four. `~/.margin/writing-rules.md` held every rule, sample and correction for every writing type, so a Slack reply loaded the cover-letter rules. Each rule went out tagged `[must-fix]`, `[should-fix]` or `[nice-to-fix]` even though the app had already collapsed strictness to Hard rule and Preference (ADR-002, revision 3), so Claude read three levels where Sam sees two. Nothing told Claude to leave untouched passages of Sam's own drafts alone, and drafting and reviewing got the same flat list.

### Decision

The CLI (still the only writer) now writes the profile in two layers:

- `~/.margin/writing-rules.md`, the entry file: how to use the profile, voice calibration, rules for all writing, and a table of writing types with counts and file paths.
- `~/.margin/writing-rules/<type>.md`: that type's rules plus its samples and corrections. Samples and corrections with no type go to `general.md`. Files for types that no longer have rules or examples are removed; nothing else in the folder is touched.

Hard rules render as a checklist ("breaking one is always a mistake"); preferences render as plain bullets ("the request, the reader, or the source can override them"). The severity tags no longer reach the agent, in the files or through the MCP server's rules tool, resource and feedback prompt. The entry file's how-to gives separate instructions for drafting, reviewing, and editing someone else's text, and the last one says to apply rules only to the passages being changed.

The entry file keeps its path, so the Codex router, Sam's skills and the guard's "see writing-rules.md" message keep working. The compliance checker's LLM audit now reads the entry file plus every type file, since it needs the whole rule set.

### Not done

- Packaging the profile as an installable agent plugin (the skill's multi-client manifest). Margin has no outside users yet, and `margin skill-install` already covers Claude Code and Codex.
- The Rust and MCP whole-profile formatters (`generate_writing_profile_markdown`, `getWritingProfileMarkdown`) still produce one file. They write nothing and no agent reads them as the profile. The Rust one still prints severity tags; it was left alone rather than changing Rust that can't be built in the cloud.

## ADR-005: First run makes a rule, and type is set by role

**Date:** 2026-11-04 · **Status:** Accepted

### Context

Sam pointed at *If This Finds You* (ifthisfindsyou.app) as a reference: every visit opens on something to read, and every claim on the page says how it is known. Margin's first run did neither. It opened on a human-voiced essay about reading with a pencil. Highlights on it were drawn but never saved, while the toasts said "Highlight saved" and "Annotations saved". The note card can't open without a saved highlight, so a new user couldn't leave a note. Making a rule took a real file, a note, Settings, a copied prompt, the Claude switch and a round trip through Claude. New installs start with no rules (fresh-user QA, Oct 9), so a stranger's first session never reached the product's payoff.

Type had drifted too. Newsreader shipped as the static build, which fixes its optical size at 18, so headings and small text used the text cut. Four places asked for Inter, which was never bundled, and `--font-sans` was used but never defined, so note threads fell back to the system face. The Reading › Font setting wrote `--reader-font-family`, but no rule read it.

### Decision

- **The sample is an AI draft with planted tells.** It's a short work email with five tells ("I hope this finds you well", "delve into", "leverage", "it's not just…", "explore this further"), followed by a second draft repeating them. It says plainly that an AI wrote it. On first launch it is written to `~/.margin/samples/first-draft.md` (once; later edits survive) and opened like any file, so highlights save and the note card works.
- **"Never write this" makes a Hard rule on the spot.** For any highlight up to 60 characters, the note card offers it. The new `create_never_write_rule` command stores a must-fix kill word for all writing types, lowercased because the guard matches kill words with `word in text.lower()`. Its `why` records where it came from ("From your mark on first-draft.md, Nov 4."). No Claude is involved. The editor's existing rule scan then underlines the phrase in both drafts, which proves the rule worked. Marking the same phrase again adds a signal and brings back an archived rule. The highlight is kept as the rule's evidence even without a note.
- **The Writing guard is offered at the moment it means something.** After the first rule, if the guard is off, a card names the phrase and the file the guard adds to `~/.claude/hooks`. It stays until answered. The default is still off.
- **Onboarding ends on the first rule or on opening your own file, never on a timer.** The 8-second welcome dismissal and the 30-second auto-complete are gone. Text with no file behind it says its highlights aren't saved.
- **Type: one stack per role.** `--font-serif` (Newsreader, variable build with `font-optical-sizing: auto`), `--font-sans` (Instrument Sans) and `--font-mono` (the system's) are defined once in `globals.css`. A test fails if a family is named anywhere else. JetBrains Mono is no longer bundled. The existing voice split stays: notes in your own voice are sans roman, and quoted authorial text is serif.

### Not done

- Measuring time to first rule with people who aren't Sam. The target is 4 of 5 strangers reaching a Hard rule within two minutes, on the QA build with a scratch `HOME`.
- Phrase rules match as literal substrings, like every kill word, so "leverage" also catches "leveraged". Word-boundary matching would have to change in the guard, the bench and the editor scan together.

## ADR-006: Polish the demo path first

**Date:** 2026-11-06 · **Status:** Accepted

### Context

Sam asked for a polish pass so Margin can be shown off, then chose to polish the path of a 90-second recorded demo first and the rest of the app after. Margin's payoff (Claude being stopped from writing what you flagged) happens outside the app, so a screen-by-screen pass can't show it; the demo has to show the whole loop in one sitting. The path was walked in the browser build (the repo's Tauri stubs, Playwright, light and dark) and ranked by how visible each problem is times how long it's on screen.

### Decision

- **The first-run hint no longer takes space in the layout.** It was in the page flow and disappeared on the first selection, so the document jumped ~34px mid-drag and the reader's first highlight landed on the wrong words. It's now a fixed pill at the bottom that ignores the pointer.
- **Phrase rules are shown as the reader marked them.** The stored rule stays lowercase because the guard matches lowercased text; the UI shows the marked phrase (kept in `exampleBefore`) when it's the same phrase. Applies to the note card, the guard offer, the style guide, the rule margin, the bench and the rule card.
- **The guard offer docks bottom right, under overlays,** instead of floating over the reading column and above the ⌘K dimmer, and it hides while Settings is open. Once the guard is on it links to the rules.
- **Writing rules is a ⌘K action** (⌘⇧M). Typing "rules" found nothing before; the product's main artifact was two levels down in Settings.
- **"Never write this" is a button,** not red text that read as an error or a delete. "Esc removes" became "Esc discards".
- **Dev:** the browser stub keeps rules in memory and `?fresh` starts with none, so the first run can be checked without the Mac.

- **A new rule visibly lands.** Three directions were mocked live (ink draws, wash then settle, and ink draws plus a count of catches outside the view). Sam picked the third: right after "Never write this", the rule's underlines draw in under every match in reading order (180ms apart), and if any match is outside the view a "Caught N more below" chip scrolls to it and washes it. In a full 1440×900 window the second draft's match is just on screen, so the chip mostly matters in smaller windows; the draw-in carries the moment either way. Reduced motion skips both animations.
- **Dark-mode yellow highlight is paler** (250,214,90 at 20% instead of 245,200,40 at 30%), which read as mustard. Chosen over a lower-half "marker" style that would have changed the highlight's shape.

- **WebKit check (Safari's engine on Sam's Mac, from a throwaway worktree):** Newsreader's optical sizing works and both faces load. It found that highlighted text went black in dark mode: the mark rules set only a background, so the text took the browser's default highlight color. Marks now inherit the text color; that, more than the yellow's tint, was the "muddy" dark highlight. The first-run hint moved to the bottom left, off the text column. The rule underline is written as separate properties after Playwright's WebKit build dropped the shorthand mid-animation (the Mac's own WebKit didn't).

### Not done yet

At narrow windows (1280×720) the note card covers the paragraph beside the selection, and React logs a set-state-during-render warning on load. Both predate this work.

## ADR-009: Adopt pstack's method, verify the UI with a committed driver

**Date:** 2026-11-12
**Status:** Proposed

**Context.** Sam asked for pstack (Lauren Tan's Cursor plugin of engineering workflows) on every thread, to give agents a better way to check and iterate on frontend and backend work. Three facts shaped how. Cloud sessions do not install plugins a repository enables in `.claude/settings.json`, so a committed plugin setting would reach Sam's Mac only. 57 of pstack's 58 skills set `disable-model-invocation`, so the model can't call them through the `Skill` tool and must read them as files, which is what pstack's own Claude Code adapter says to do. And pstack's UI verification step points at `control-ui`, a browser and Electron driver from another Cursor plugin, which cannot reach a Tauri webview.

**Decision.** `scripts/pstack` fetches pstack at a pinned commit in cloud sessions and prints its path. `CLAUDE.md` tells code threads to follow poteto-mode and lists where Margin's rules override it. pstack's `create-verification-skill` recipe produced `.claude/skills/verify-margin/`: a Playwright driver for the stub build that asserts on the Tauri commands each action sends, a feature map, and the four verification lanes. `.gitignore` now tracks that one skill folder and keeps the rest of `.claude/` private.

**Why not the plugin install alone.** It would load pstack on Sam's Mac and nowhere else, and threads run in the cloud. Pinning also means an upstream pstack change reaches Margin only when someone bumps the commit.

**What this does not fix.** The driver runs Chromium against stubs, so it proves the UI sent the right command, not that Rust handled it or that WebKit renders it the same. A real-app lane in the cloud (tauri-driver with WebKitWebDriver under Xvfb) would close that gap and is the next candidate.
