## The Autoresearch Discovery

The biggest finding from exploring the codebase: **Margin already has an empirically-validated answer to part of this question, and an automated optimization loop that has never been activated.**

### What exists

`mcp/scripts/autoresearch/` contains:
- `loop.ts` — Karpathy-style autoresearch orchestrator: modify coaching-prompt.md → eval → keep if better → revert if worse → repeat
- `eval.ts` — 27-sample evaluation harness (9 writing types × 3 samples), scores against compliance metric
- `coaching-prompt.md` — the template with `{{RULES}}`, `{{TYPE}}`, `{{REGISTER}}`, `{{PROMPT}}` placeholders
- `program.md` — research program defining 5 competing architectures and their results
- `generators/arch-f-aegis.ts`, `generators/arch-h-dspy.ts` — two architecture generators
- `rule-study/` — rule audit, extraction, and synthesis pipeline
- `ideas.md` — ranked backlog of untested optimization levers
- `session.md` — status: **"Not yet started. Run `npx tsx mcp/scripts/autoresearch/loop.ts` to begin."**

### Empirical architecture results (from program.md)

The autoresearch program ran manually across 5 architectures before the automated loop was built:

| Architecture | Description | Pass Rate |
|-------------|-------------|-----------|
| A: Rules only | 259 rules as prose instructions | 51.9% |
| B: Exemplars only | 10-20 paragraphs of Sam's best writing | 55.6% |
| C: Editor (two-pass) | Write freely, then edit against rules | 63.0% |
| D: Corrections only | Raw correction diffs as context | 66.7% |
| E: Hybrid (corrections + high-signal rules) | signal_count ≥ 2 OR severity = must-fix rules + corrections | **76.9%** (72.3% mean across 3 runs) |
| H: DSPy-optimized | MIPROv2 optimized coaching prompt | ~68-70% (within noise of E) |

**Key finding from Tier 1:** Architecture H (DSPy optimization) matches Architecture E but doesn't exceed it. The conclusion in program.md: **"data layer > presentation layer."** Optimizing *which* corrections and rules load matters more than *how* the coaching prompt presents them.

### Why hasn't the loop run?

Three blockers:

1. **Missing generators for architectures a–e.** Only `arch-f-aegis.ts` and `arch-h-dspy.ts` exist in `generators/`. The eval harness imports `arch-a-rules.ts` through `arch-e-hybrid.ts` but those files don't exist. Running `npx tsx eval.ts` (default, architecture A) would fail immediately.

2. **`margin export coaching-prompt` doesn't exist.** The `/writing-voice` SKILL.md references `margin export coaching-prompt --type <type>` to load type-specific coaching context. The Go CLI (`cli/cmd/export.go`) only has `wait`, `profile`, and `codex` subcommands. This command doesn't exist on main or any branch. The coaching-prompt.md template's `{{RULES}}` placeholder has no CLI to fill it.

3. **No results.tsv yet.** `loop.ts` reads `results.tsv` to determine the baseline. Without at least one eval run to establish a baseline, the loop has nothing to improve on.

## Reference Patterns

How the 11 external sources map to Margin's specific situation.

### Every.to AI Style Guide

Anti-patterns blacklist is their highest-value section — which maps to Margin's kill-word and slop-pattern enforcement. Their key insight: **paired before/after examples teach models faster than abstract rules.** They call this "one of the most useful sections" in a style guide.

Margin gap: 94% of corrections have NULL polarity. The "paired examples" pattern requires both the violation (corrective) and the corrected form (positive). Without polarity tagging, paired examples can't be assembled. Margin is at their "Level 3" (automated enforcement) but lacks the data quality to implement their highest-value technique.

Their three maturity levels also validate Margin's overall architecture: manual paste → project context → automated pipeline with feedback loops. Margin is at Level 3 and the work from here is refinement, not architecture change.

### Dropbox DSPy (GEPA)

45% NMSE reduction using constrained optimization from a curated instruction library — selecting the best combination of existing rule-bullets rather than rewriting prompts wholesale. This maps directly to Margin's situation: the rules *are* the instruction library, and the autoresearch program has already been exploring selection strategies.

The key lesson for Margin: Tier 1.5 already applied GEPA to Margin's rules (found 14 repeat corrections, applied 13 fixes via launchd). The infrastructure is running. The gap is that DSPy optimization showed H ≈ E — no meaningful lift beyond the hybrid architecture. Per program.md, this reinforces "data > presentation."

### Hamel's evals-skills

The `write-judge-prompt` + `validate-evaluator` two-stage pattern: define what "good" means as a judge prompt, then validate that your judge is calibrated. This maps to Margin's compliance-check.ts, which scores outputs on 5 dimensions but has never been validated against Sam's actual corrections (eval calibration is listed as a "standing research priority" in program.md).

The deeper insight: **the skill IS the enforcement, not just context loading.** The skill should contain its own eval loop, not be a passive context-injector that hopes the model complies.

### @toddsaunders (two tweets)

A meta-skill that builds and optimizes other skills: interviews you to understand the domain, classifies the skill type, drafts SKILL.md, self-reviews against quality criteria, generates test cases, and iterates on failures. The skill-creator plugin at `~/.claude/plugins/marketplaces/anthropic-agent-skills/skills/skill-creator/` already implements this pattern with `run_eval.py`, `run_loop.py`, and grader/analyzer agents.

For Margin: the skill-creator eval loop could improve *how the skill presents rules* (the SKILL.md instructions). But given Tier 1's finding that presentation layer < data layer, this is likely lower-leverage than fixing the missing generators and running the autoresearch loop first.

### @trq212 (Anthropic)

Skills as folders with scripts, data, and assets — not just markdown files. Business process skills use log files for session-to-session consistency. Validates Margin's skill folder structure. The "log file for consistency" pattern is exactly what `feedback.log` implements in Ole Lehmann's work — and it's what Margin does at the DB layer (more structured, more powerful).

### @itsolelehmann (feedback.log)

Add a feedback.log to the skill folder. The skill reads it at session start and appends corrections during the session. By session ~10, corrections drop off. By ~20, first drafts are near-complete. **This validates Margin's entire correction→rule pipeline** — it's the same loop, but with a structured DB instead of a text file. The implication: Margin's architecture is right, the question is whether it's been exercised enough.

### @itsolelehmann (autoresearch loop)

Karpathy's autoresearch pattern applied to Claude skills: make one small change to the coaching prompt, score against a yes/no checklist, keep the change if the score improved, revert if not, repeat. Landing page copy skill went from 56% → 92% pass rate with zero manual work.

**This is the highest-leverage external finding.** Margin already has `loop.ts` implementing this exact pattern. The scoring infrastructure exists (`adversarial-test.ts` + `compliance-check.ts`). The coaching prompt template exists. The only things missing are: (1) the missing generators so the eval can run, and (2) a baseline `results.tsv` to improve from.

### @lydiahallie

Dynamic content injection in SKILL.md: `!command` syntax runs a shell command at skill invocation time and injects the output inline. The model only sees the result, not the command. This enables token-efficient, type-specific rule loading: instead of embedding all 259 rules statically, the skill can run `sqlite3 ~/.margin/margin.db "SELECT ..."` at invocation and load only the relevant subset.

This is the integration path for loading rules into the skill without `margin export coaching-prompt` (which doesn't exist). A `!sqlite3` inline query can filter rules by writing_type and signal_count at invocation time.

### Kieran Klaassen

"Ten specific rules beat 100 generic ones." With 259 rules (244 general), rule selection is a higher-leverage optimization than rule volume. The autoresearch ideas backlog already identifies this as "tighter rule threshold" (test: signal_count ≥ 3 instead of ≥ 2). The DSPy GEPA work is essentially rule selection — selecting the highest-signal instruction bullets.

### Simon Willison

Skill shell costs only a few dozen extra tokens, with full details loaded only when requested. The per-style overhead is minimal. Per-style skills won't create a token problem — the rules payload is what matters, and that's filterable by type.

### Katie Parrott

"The gap between 'I built a skill' and 'the skill works reliably' turned out to be wider than expected." Validates the need for the eval loop, not just skill authoring. A SKILL.md without an eval harness is a hypothesis, not a system.

## Gap Analysis

The core gap: **42% of writing rules require model judgment, and there's currently no verification that the model follows them.**

The `voice_loader.py` hook injects `writing-rules.md` at session start. But injection ≠ compliance. The model can read the rules and still produce tone-deaf, rhythm-less prose that passes the mechanical hook.

The two skills (`/writing-voice`, `/writing-quality-gate`) address this gap through invocation — but both require manual invocation, and neither is connected to the correction→rule feedback loop. You can give Sam a correction in Margin, synthesize it into a rule, export the rule to the writing guard, and still have Claude ignore it on the next cover letter because the skill wasn't invoked.

The autoresearch program quantifies this gap: Architecture A (rules only, current default) achieves 51.9% pass rate. Architecture E (hybrid) achieves 72.3%. That 20-point gap is the difference between "rules exist" and "the model uses them well."

## Architecture Options

### Option 1: Single optimized skill

Extend `/writing-voice` (or replace it) with an optimized coaching context that loads rules dynamically via Lydia Hallie's `!command` pattern, includes a post-write compliance check, and is systematically improved via the autoresearch loop.

**Strengths:** One skill to maintain, one optimization target, simpler mental model.

**Weaknesses:** All writing types get the same skill structure, even if their needs differ significantly. Cover letters and Slack messages have genuinely different compliance requirements.

**Data support:** With 94% general rules and 83% untyped corrections, there isn't enough type-specific signal to differentiate today. A single skill is what the data supports.

### Option 2: Per-style skill family

Build a separate skill for each writing type (cover-letter, outreach, slack, email, blog, etc.), each loading type-specific rules and corrections.

**Strengths:** Each skill can be optimized for its writing type's specific compliance requirements. Cover letter skills can be more aggressive about structural patterns; Slack skills can be more permissive about fragments and informality.

**Weaknesses:** Requires substantially more type-specific correction and rule data to differentiate. With 94% general rules and 0 type-specific corrections, the per-style skills would load nearly identical content today. The differentiation would only emerge after significant correction backfill.

**Data support:** Not warranted with current data. Revisit after 50+ corrections per writing type with polarity tags.

### Option 3: Hybrid (parameterized skill + autoresearch loop)

A single skill parameterized by writing type, combined with an active autoresearch loop that continuously improves the coaching prompt architecture. The skill loads type-relevant rules via `!sqlite3` query (filtering by writing_type and signal_count), and the autoresearch loop optimizes the coaching prompt using the eval harness.

**Strengths:** Single skill to maintain, but type-aware rule loading. The autoresearch loop can test per-type vs. general loading as a tunable lever without requiring separate skills. If per-style eventually proves beneficial, the autoresearch loop will find it empirically.

**Weaknesses:** More complex than Option 1. Requires building the missing generators (a–e) and establishing a baseline results.tsv before the loop can run.

---

## Recommendation: Option 3 (Hybrid + autoresearch loop)

**The highest-leverage move is activating the autoresearch loop, not redesigning the skill.**

Margin already has 72.3% pass rate from Architecture E, built through manual experimentation. The automated loop exists to push beyond that without manual work. Ole Lehmann demonstrated 56% → 92% using the same pattern. The expected lift from activating `loop.ts` against the ideas backlog (register-specific tuning, type-filtered corrections, tighter rule threshold) is material.

The skill redesign is secondary to this. The reason Architecture E outperforms Architecture A by 20 points is not because the skill is structured differently — it's because E loads *different data* (corrections + high-signal rules instead of all 259 rules). Optimizing the skill's SKILL.md instructions without fixing the data pipeline is optimization on the wrong surface.

**Priority order:**

1. Build missing generators (arch-a through arch-e) so the eval harness can run
2. Establish a baseline: run `npx tsx mcp/scripts/autoresearch/eval.ts --arch e` to get a starting results.tsv
3. Run the autoresearch loop against the high-priority ideas backlog (register tuning, type filtering, tighter threshold)
4. Fix the broken skill reference: update `/writing-voice` SKILL.md to use `!sqlite3` query instead of `margin export coaching-prompt --type <type>`
5. Add post-write compliance: wire `compliance-check.ts` into the skill workflow (inline check after write)

## Data Prerequisite Assessment

**Per-style skills require data that doesn't yet exist.**

Current distribution:

| Writing type | Corrections | Rules |
|-------------|-------------|-------|
| general | 43 | 244 |
| cover-letter | 0 | 9 |
| outreach | 0 | 5 |
| blog | 0 | 1 |
| NULL (untyped) | 206 | 0 |

Two gaps block the highest-leverage autoresearch improvements:

**Gap 1: 83% untyped corrections.** The ideas backlog's #1 item is "correction selection by writing type." But 206 of 249 corrections have NULL writing_type, making type-filtered selection effectively impossible. The autoresearch eval tests 9 types × 3 samples — but 8 of those 9 types have no type-specific correction signal.

**Backfill feasibility:** Corrections have `document_title`, `document_source`, and `document_path` fields. Many paths likely contain type signals (e.g., paths containing "cover-letter", "outreach", "blog"). The `margin_update_correction_writing_type` MCP tool exists for single updates. A batch script using heuristic inference from document paths could recover a significant portion of the NULL types.

**Recommendation:** Write a one-time backfill script that infers writing_type from document_path patterns before building per-style infrastructure. Estimated effort: ~2 hours. Expected recovery: 30-60% of NULLs, enough to get meaningful type-specific correction samples.

**Gap 2: 94% NULL polarity.** The Every.to style guide's highest-value technique is paired before/after examples (violation + correction). Architecture D (diff-based preference learning) uses the same pattern. Neither works without polarity tagging. Only 14 of 249 corrections are tagged "corrective"; none are tagged positive.

**Backfill feasibility:** Correction text often implies polarity ("don't use X" → corrective, "good use of Y" → positive). A classifier could infer polarity from the correction text with reasonable accuracy. But polarity backfill is lower priority than writing_type backfill — it blocks a future technique (paired examples) rather than the immediate high-value lever (type-filtered correction selection).

**Recommendation:** Backfill writing_type first (higher ROI, unlocks autoresearch levers). Polarity backfill after per-style analysis is feasible.

## Prototype Spec

**Target:** A single PR that (a) fixes the broken skill reference, (b) adds type-aware rule loading, (c) wires post-write compliance, and (d) enables the autoresearch loop to run.

### (a) Skill structure

Keep `/writing-voice` and `/writing-quality-gate` as separate skills. Don't merge them — the distinction between "context loading before write" and "review after write" maps to two genuinely different workflows, and merging would make the 927-line quality gate harder to optimize.

Update `/writing-voice` SKILL.md to:
- Replace the broken `margin export coaching-prompt --type <type>` call with a `!sqlite3` inline query
- Add a post-write compliance step that calls `compliance-check.ts`

### (b) Rule loading — replace broken CLI call

The current SKILL.md references `margin export coaching-prompt --type <type>` which doesn't exist. Replace with Lydia Hallie's `!command` pattern:

```
!sqlite3 ~/.margin/margin.db "
SELECT rule_text
FROM writing_rules
WHERE (writing_type = '{TYPE}' OR writing_type = 'general')
  AND (signal_count >= 2 OR severity = 'must-fix')
ORDER BY severity DESC, signal_count DESC
LIMIT 30
"
```

This loads type-relevant, high-signal rules at invocation time without any CLI command. Token-efficient — only loads the relevant subset, not all 259 rules.

### (c) Post-write compliance

After Claude writes, the skill should invoke the compliance checker inline:

```
After writing, run: npx tsx mcp/scripts/compliance-check.ts --file {OUTPUT_FILE}
Report any must-fix violations before handing off.
```

This closes the feedback loop: write → check → report violations → correct. Currently, compliance checking only runs from the CLI manually.

### (d) Autoresearch loop activation

Three steps to make `loop.ts` runnable:

**Step 1:** Build missing generators. The eval harness imports `arch-a-rules.ts` through `arch-e-hybrid.ts` but only `arch-f-aegis.ts` and `arch-h-dspy.ts` exist. The generators need to be built for architectures a–e. Each generator implements:
```typescript
export async function generate(prompt: string, type: string, register: string): Promise<string>
```
Architecture A (rules) is the simplest — load rules from DB, build coaching prompt, call Claude. This establishes the baseline.

**Step 2:** Run a baseline eval: `npx tsx mcp/scripts/autoresearch/eval.ts --arch e`
This creates `results.tsv` with the Architecture E baseline (~72% pass rate).

**Step 3:** Start the autoresearch loop: `npx tsx mcp/scripts/autoresearch/loop.ts`
The loop reads `ideas.md`, applies one modification to `coaching-prompt.md`, evals, keeps or reverts, appends to `results.tsv`, and iterates. The primary metric is the pass rate already defined in eval.ts (zero mechanical issues AND dimension score ≥ 35/50).

### (e) Hook boundary (non-negotiable)

The hook's 44 kill words, 100 slop patterns, 27 auto-corrections, and 1 heading pattern stay in `writing_guard.py`. These are the fail-closed layer — they block the tool call and cannot be bypassed by model behavior. Moving any of these to the skill loses the "can't be ignored" guarantee.

The skill handles what the hook can't: voice-calibration rules (25), editorial rules (9), tone/rhythm rules, structural patterns that require judgment. These are fail-open: the model can ignore them, which is why the autoresearch loop exists.

### (f) Three optimization loops — sequencing

Three independent optimization loops exist:

| Loop | What it optimizes | Status | Priority |
|------|------------------|--------|----------|
| Autoresearch (`loop.ts`) | End-to-end coaching prompt via iterate-score-keep/revert | Never run | **First** |
| DSPy (`pipeline.py`) | Coaching prompt content via MIPROv2 instruction selection | Infrastructure built, 0 runs | Second (Tier 1 showed H≈E — low marginal lift) |
| Skill-creator (`run_loop.py`) | SKILL.md instructions via eval loop | Available | Third (presentation < data per Tier 1) |

Run autoresearch first — it tests the full pipeline and builds the evidence base. Re-evaluate the others after autoresearch has converged. Given Tier 1's finding that DSPy/H ≈ E (no lift), DSPy may not be worth running again until the data layer improves (writing_type backfill, polarity backfill).

### (g) Primary metric

The autoresearch eval already defines the primary metric: **pass rate** (% of 27 samples with zero mechanical issues AND dimension score ≥ 35/50).

The honest caveat: this proxy metric has never been calibrated against Sam's actual corrections per document. Optimizing against an uncalibrated proxy risks Goodharting. The program.md calls this out as "Tier 2: Audit foundation" (not started). Run Tier 2 calibration after the first autoresearch loop converges, not before — you need results to calibrate against.

**Test scenario (cover letter):**

> "I'm writing a cover letter. Which skill fires? What rules load? What gets checked by the hook vs. skill?"

1. `/writing-voice` fires (manual invocation or via `voice_loader.py` hook)
2. The `!sqlite3` query loads rules where writing_type IN ('cover-letter', 'general') AND (signal_count >= 2 OR severity = 'must-fix'). Currently: 9 cover-letter rules + ~150 qualifying general rules ≈ ~30 loaded (LIMIT 30)
3. The hook checks mechanically against 44 kill words, 100 slop patterns, 27 auto-corrections, 1 heading pattern — immediately on Write
4. Post-write: the skill invokes `compliance-check.ts`, which scores on 5 dimensions and reports violations
5. "How do I run the eval loop?" — `npx tsx mcp/scripts/autoresearch/eval.ts --arch e` for a one-shot eval, `npx tsx mcp/scripts/autoresearch/loop.ts` for the self-improving loop
6. "What metric tells me it got better?" — pass rate in `results.tsv`. Baseline: ~72.3% (Architecture E). Target: >85% before per-style differentiation becomes worth the data investment.

## Summary

The question isn't "should we use skills" — Margin already has two. The question is "what's blocking them from working reliably?"

Three blockers, in priority order:

1. **Missing generators a–e** prevent the autoresearch eval from running. Without a baseline, the loop can't improve anything.
2. **`margin export coaching-prompt` doesn't exist** on any branch, so `/writing-voice` is broken for type-specific coaching contexts. Fix: `!sqlite3` inline query.
3. **83% untyped corrections** mean the highest-leverage autoresearch lever (type-filtered correction selection) can't be tested. Fix: writing_type backfill from document paths.

The recommendation is **Option 3: single parameterized skill + active autoresearch loop.** Build the missing generators, establish a baseline, run the loop against the ideas backlog. The skill optimization (Tier 3 in the program.md) follows naturally once the loop has converged and identified which coaching prompt architecture performs best. Per-style skills come last — only after backfill makes the type-specific data meaningful.

The autoresearch loop is the needle-mover. Everything else is scaffolding.
